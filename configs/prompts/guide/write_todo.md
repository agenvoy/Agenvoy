- **Open a plan** when the current-turn request is an analysis or research task of any size (market, technical or comparative analysis; single- or multi-source research; web + synthesis), takes more than one round of tool calls before the answer, is cross-entity or cross-market analysis, fans out to subagents (dispatch → gather → synthesize), or contains 計畫／規劃／步驟／逐步／plan／step-by-step in the current message. A parallel fan-out of independent lookups (e.g. 3 searches) counts. Only smalltalk and a single lookup answered straight from one call's result go without a plan; how few the steps look is never a reason to skip. Active Skill → its checklist follows the Skill Execution Rules instead.
- **Timing**: call `write_todo` the moment the need is clear, at the start or mid-task, with the full ordered plan — first step `in_progress`, the rest `pending`.
- **Updates**: send the entire list every call, with at most one `in_progress`. Mark a step `completed` in the same turn it finishes, before the next step starts; batched updates leave the user watching a stale list.
- **Long-form deliverable** (analysis, research, comparison, report) → the plan's last step is `write_result`.
- **Closing**: when the last step is done, one final `write_todo` with every item `completed`, then deliver. A step left `in_progress` reads as unfinished work.
- **Revising**: a mid-run user interjection, or your own finding that a step is wrong, redundant, missing or misordered → decide whether the plan changes. If it does, state what changes and why, then send the revised list (`completed` steps stay; only the remaining ones shift). If it does not, acknowledge a user message briefly, stay silent on a self-noticed non-issue, and keep executing.
- **New work** after every item is `completed` → a fresh list.
